1. Project at a Glance

GapAnalyzer is a web tool that reads a resume and a job description side by side and tells the applicant exactly what is missing: a match percentage, matched skills (yellow highlighter), missing skills (red pen), category breakdowns, actionable suggestions, and an example rewritten bullet.

One-liner: “A tool that reads a resume and a job posting side by side, tells the user exactly what skills or keywords they're missing — using both simple keyword matching and smarter, meaning-based AI matching — and then generates an updated resume for them.”

  • Problem: ATS (Applicant Tracking Systems) reject qualified candidates on wording alone (“led a team” vs “management experience”); job seekers never learn why they were rejected.
  • Users: students and job seekers, career centers, anyone applying to several similar postings.
  • Current scope (mid-sem): keyword-based gap detection — PDF/DOCX/TXT extraction → skill dictionary + regex → TF-IDF/overlap scoring → results UI, deployed end-to-end.
  • Future scope (end-sem): embeddings-based semantic matching (sentence-transformers), LLM-generated resume rewrite, real-user testing.
Architecture in one sentence A stateless two-process architecture: a Next.js 16 frontend (rendering + upload UX) calls a FastAPI backend (document parsing + NLP scoring) over a single JSON API, passes results between pages with sessionStorage, and renders them through a fixed 22-component design system.

2.2 Why two separate processes

  • Separation of concerns: the frontend owns presentation and UX state; the backend owns document parsing and NLP. Neither leaks into the other — the boundary is one documented JSON contract.
  • Different runtimes: Python has the mature PDF/DOCX/scikit-learn libraries (pdfplumber, python-docx, scikit-learn); React/Next.js has the best UI ergonomics. Splitting lets each side use its ecosystem's best tool.
  • Independently deployable: the frontend goes to Vercel, the backend to Render/Railway — configured by two env vars (NEXT_PUBLIC_API_URL, ALLOWED_ORIGINS).
  • Cost of the split: CORS must be configured, and two servers must be kept in sync with the contract — mitigated by Pydantic models + TypeScript types + a 21-check smoke test (see §9, §10).

6. The Matching Algorithm (Deep Dive)

6.1 Stage A — skill extraction (deterministic keyword matching)

  1. Load the 117-entry dictionary once at import; compile each skill into one alternation regex over its name + aliases.
  2. Guard every alternative with (?<!\w) … (?!\w) — word-edge guards, so “java” never matches inside “javascript”, “js” never matches “json”, “r” can't match “report”.
  3. Separators are interchangeable: an alias like unit-testing is compiled as unit[\s_\-]+testing, so “unit testing”, “unit_testing” and “unit-testing” all hit.
  4. Longest alias wins at each position (fragments sorted by length, descending) so the most specific form matches first.
  5. count_mentions(text) runs every pattern over the lowercased text → {skill_name: occurrences} for the JD (what's required) and the resume (what's present).

6.2 Stage B — scoring

coverage  = Σ (mentions of required skills found in resume)  /  Σ (mentions of required skills)
cosine    = cosine_similarity( TF-IDF(resume), TF-IDF(jd) )  // 1–2 grams, english stop words

match_score = round( 100 × ( 0.6 × coverage + 0.4 × cosine ) )
              // if the JD contains ZERO dictionary skills → match_score = round(100 × cosine)
              // result clamped to [0, 100]
  • Coverage is mention-weighted: a skill the posting repeats (CI/CD ×3) counts triple — mirroring how loudly the posting asks for it. Term-frequency weighting, the same idea TF-IDF applies to text.
  • TF-IDF vectorizes both texts together as a 2-document corpus: term frequency inside each document × inverse document frequency across the pair; unigrams + bigrams; English stop words dropped; then cosine similarity ∈ [0, 1] of the two vectors. It catches topical/wording overlap the dictionary doesn't know about.
  • Why the blend: coverage is precise but blind to anything outside the dictionary; cosine is broad but easily inflated by shared boilerplate. 60/40 keeps dictionary evidence in charge while letting general textual similarity move the needle.
  • Category scores = matched ÷ required per category (technical/tools/soft); a category the JD never asks for scores 100 (no gap).

Worked example

Arithmetic JD mentions: React ×3, Docker ×2, AWS ×1 (total 6). Resume contains React + Docker but not AWS → coverage = (3+2)/6 = 0.833 · cosine = 0.15 → score = 100 × (0.6 × 0.833 + 0.4 × 0.15) = 100 × (0.500 + 0.060) = 56.

6.3 Stage C — the extras

  • Missing/missing lists: sorted alphabetically (matched) and by mention count descending (missing) so the loudest gaps render first.
  • why strings: taken verbatim from the dictionary's why field (copy-deck text), else a generated “Mentioned N times in the posting but not found in your resume.”
  • Recommendations: top-3 missing skills → “Add a bullet mentioning {skill} — the posting emphasizes it N times.” (singular variant for N=1).
  • diff_example heuristic: take the top missing skill; collect the JD context words within ±40 chars of each mention; split the resume into sentences (≥15 chars, bullet markers stripped); pick the sentence with the most context-word overlap that has an insertion anchor (a JD-required skill mention); insert “{skill}, ” before the earliest anchor. Returns {"", ""} when no sensible anchor exists. Documented as the mid-sem heuristic — the LLM replaces it end-sem, contract field unchanged.
  • job_title / company: best-effort (first short line; Company:/About us: labelled line) — parsed but not yet rendered by the screens.

8. End-to-End Data Flow

  1. Input — user drops resume.pdf and pastes the JD on /upload; client pre-checks type + size.
  2. Submit — FormData{resume, job_description} → fetch POST ${NEXT_PUBLIC_API_URL}/api/analyze; UI enters the analyzing checklist (visual pacing, 2.8 s floor).
  3. Parse — FastAPI parses multipart; extraction.py picks the strategy by extension and returns clean text (or 400/413/422).
  4. Detect — skills.py counts dictionary skills in JD (required) and resume (present) via compiled regexes.
  5. Score — matching.py blends weighted coverage (0.6) with TF-IDF cosine (0.4), derives category scores, missing/matched lists, recommendations, the diff example, and JD metadata.
  6. Validate + serialize — Pydantic AnalysisResponse enforces the contract, FastAPI returns JSON 200.
  7. Handoff — client validates the payload, writes sessionStorage["analysis"], waits out the checklist beat, router.push("/results").
  8. Render — /results reads sessionStorage (else the mock), GSAP sequence plays (stamp → bars → sheets → chips → verdict). /report deep-dives the same payload (missing.why, recommendations, diff).
  9. Errors — any failed step lands back on the form with a copy-deck message and the input preserved.
Verified E2E A real fixture run produced: path=/results, stamp “31 percent match”, categories 67/50/0, matched CSS/DOCKER/HTML/JAVASCRIPT/KUBERNETES/REACT, missing led by CI/CD — genuine pipeline output, not the 68% mock. A zero-overlap “pastry chef” resume produced 0% → “NO KEYWORDS MATCHED” + NEEDS WORK, exercising the empty-state path.

9. Cross-Cutting Concerns

9.1 CORS

  • Browser same-origin policy blocks the browser→backend call unless FastAPI opts the frontend origin in. The CORSMiddleware allows GET/POST from origins in ALLOWED_ORIGINS (comma-separated env var).
  • Defaults: localhost:3000, localhost:3100, 127.0.0.1:3000, 127.0.0.1:3100. At deploy, the frontend's real origin must be appended — this plus NEXT_PUBLIC_API_URL is the entire deploy configuration for the pair.
  • Gotcha learned in practice: a stale 127.0.0.1:8000 process shadows a new 0.0.0.0:8000 one on loopback — kill all listeners before restarting the backend, or old CORS rules keep answering.

9.2 State & persistence

  • No database. Analyses are computed on demand, stored only in sessionStorage (per-tab, cleared when the tab closes) and re-fetched implicitly by re-running an analysis.
  • Why: nothing to secure, migrate, or seed; the demo can't leak resumes; the backend stays a pure function. The plan lists a DB as optional — a history feature would be the reason to add one later.
  • Mock fallback: direct visits to /results//report render MOCK_ANALYSIS (68%), so screens are never blank in review or demos.

12. Design Decisions — Viva Q&A

Why FastAPI instead of Flask (or a Node backend)?
FastAPI is async-native and schema-first: request parsing (multipart files + form fields), validation, serialization, and OpenAPI docs come from one declaration — the response_model literally locks our contract. Pydantic gives the same “shape safety” that TypeScript gives the frontend, in Python. Flask would need extra libraries for multipart validation and response schemas; a Node backend would have struggled with PDF/DOCX parsing (pdfplumber/python-docx are best-in-class) — that ecosystem choice drove the split.
Why is the system split into a frontend server and a backend server?
Different runtimes for different strengths: React/Next.js for UI ergonomics and rendering, Python for NLP libraries. The boundary is one documented JSON API, so either side can be swapped or deployed independently (Vercel + Render). The costs — CORS and contract drift — are handled by ALLOWED_ORIGINS, Pydantic/TS mirrored types, and the smoke test.
Why is there no database?
The tool is stateless by design: an analysis is a pure function of (resume, JD) and lives only in sessionStorage for the page flow. Nothing to secure, no resume data at rest (a privacy win), no migrations. The semester plan lists a DB as optional — we'd add one only for a “history of past analyses” feature.
Why a skill dictionary + regex instead of spaCy, an LLM, or embeddings?
It's the mid-sem milestone's stated approach and it's deterministic, fast (milliseconds), explainable, and free — every match can be traced to a specific alias in a specific entry, and why strings come from the dictionary. For ~117 well-chosen skills with aliases it covers real job postings well. The end-sem upgrade adds sentence-transformers embeddings for paraphrase coverage (“led a team” ≈ “management experience”) — keyword matching can't do that by construction.
What exactly is TF-IDF, and how is it configured here?
Term Frequency – Inverse Document Frequency: weight each word by how often it appears in a document (TF) discounted by how rare it is across the corpus (IDF) — common words vanish, distinctive words dominate. We fit one vectorizer on both texts (a 2-document corpus) with stop_words="english" and ngram_range=(1,2) (single words and word pairs, so “unit testing” survives), then take the cosine similarity — the angle between the two vectors — as the 0.4 term. It measures topical/wording overlap without knowing a single skill name.
Why 0.6 coverage + 0.4 cosine? What if the JD has no known skills?
Coverage (dictionary, mention-weighted) is precise but incomplete; cosine is broad but noisy. Weighting coverage 60% keeps the explainable signal in charge. If the JD contains zero dictionary skills, coverage would be meaningless (division by zero / always 0), so the score falls back to cosine alone. Both paths are smoke-tested; scores are clamped to [0,100] and rounded to an int.
Why the word-boundary regex guards — isn't substring matching simpler?
Substring matching produces embarrassing false positives: “java” inside “javascript”, “js” inside “json”, “r” inside “report”. Guards (?<!\w)…(?!\w) make matches whole-word, while allowing separators to vary so “unit testing” hits “unit-testing”. Ambiguous bare tokens (“go”, “r”) are simply omitted from the dictionary. Longest-alias-first ordering prevents partial alternation matches.
How do you keep frontend and backend from drifting apart?
Three layers: (1) Pydantic response_model — the server can't emit an invalid payload; (2) TypeScript AnalysisResult mirrors it and the client runtime-checks match_score before trusting a response; (3) 21 smoke checks assert field-by-field. The contract is written down once in context.md §9 — both sides cite it.
Why multipart/form-data for the request?
The payload contains a binary file (PDF/DOCX) plus text fields; JSON can't carry a file without base64 bloat. Multipart is the HTTP standard for that (boundary-delimited parts), and FastAPI parses it via python-multipart. A future “paste resume” mode would send plain resume_text instead.
What is CORS and why does ALLOWED_ORIGINS exist?
Browsers enforce that a page from localhost:3100 may not read responses from localhost:8000 unless the API explicitly permits that origin (same-origin policy). FastAPI's CORS middleware answers the browser's preflight and adds the allow headers. ALLOWED_ORIGINS makes that list environment-driven so dev ports and the deployed domain are one env var away — and it's the classic source of “works locally, 400/403 in production” bugs, which is why it's called out in the deploy plan.
Why Next.js App Router — and what's server vs client here?
App Router gives file-system routing, static generation for the landing pages, and next/font optimization. Everything interactive (upload form, analyzing phase, results/report data reads) is a "use client" component; layout and static structure stay server-rendered. Next 16 has breaking changes vs older versions, so the repo ships an agent note to read its bundled docs before writing code.
Why pass results through sessionStorage instead of props or a URL?
Props can't cross a route change, and URLs would put a full analysis payload (and resume-derived content) in history/logs. sessionStorage is per-tab, survives navigation, clears when the tab closes — the right lifetime for a one-shot analysis. On missing data the screens fall back to a mock, so direct visits still render a valid screen. Cost: no cross-device/shareable link (that's what the OG image + future backend storage are for).
Why Tailwind v4 with a CSS @theme block instead of a config file or CSS-in-JS?
Tailwind v4 is CSS-first: tokens are declared once as CSS variables in @theme (colors, fonts, shadows) and automatically become utilities — bg-paper, text-ink, font-display. That single block is the executable mirror of the design system, so “no new colors without updating DESIGN_SYSTEM.md” is enforceable in one place. Utilities keep markup component-first with zero one-off stylesheets; no CSS-in-JS runtime cost.
Why GSAP rather than CSS animations or Framer Motion?
The screens need authored sequences (stamp settles → bars fill → sheets rise → chips swipe → verdict lands) with staggers, scroll triggers, and SVG path draws — choreography that CSS keyframes express poorly and React re-renders can break. GSAP timelines are imperative and reversible; gsap.context + a revert on unmount keeps re-renders clean. It also ships ScrollTrigger, and the whole layer is gated by prefers-reduced-motion. A user request chose GSAP explicitly; CSS remains only for hover/press micro-feedback.
How is the project tested? Why no frontend unit tests?
Backend: 21 deterministic contract checks (all file formats + all error codes + exact copy strings) run against the live API. Frontend: npm run build (typecheck + lint + static generation) plus a comp-first visual loop — headless-Chrome screenshots compared against approved designs, with a machine-readable facts: line for assertions and an E2E mode that drives the real pipeline. Unit tests for pure presentational components were judged low-value against that; this is a documented trade-off.
What are the limitations of the current approach?
(1) Keywords only — paraphrases with no shared vocabulary never match; (2) dictionary coverage — niche skills outside the 117 entries are invisible to coverage (cosine partially compensates); (3) no OCR — scanned PDFs return a clean 422; (4) heuristic diff — the suggested bullet is a pattern insertion, not a rewrite; (5) no persistence/share; (6) not yet deployed. Each maps to a planned end-sem item (embeddings, LLM rewrite, resume generator, sample-data testing, deploy).
What changes end-sem, and does the architecture support it?
Weeks 8–9 add sentence-transformers: embeddings for resume and JD/skill phrases, cosine in vector space, and a tuned similarity threshold — slotting into matching.py behind the same contract, so the UI is untouched. Week 12 swaps the heuristic diff_example for an LLM call (field already exists). The layered design (extraction → detection → scoring → contract) means each upgrade replaces one module, not the system.
